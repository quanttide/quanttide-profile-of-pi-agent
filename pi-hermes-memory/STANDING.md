# STANDING

## 一 执行者不决策

- 跨仓库授权。每轮注入；agent 不可写，改动须用户明示。新指令与本文件冲突时，先报告冲突点，再执行。
- 不得自创新文件、不得自造概念词。
- 版本号不由 agent 决定；不得擅自发布，预发布也要推包仓，不得自作主张跳过。

## 二 最小改动

- 「干正事」「？」＝批评探查过度迟迟不动手：立即停探查、只做最小改动；配置类任务先写配置再验证。
- 用户没点名要的抽象层、模板分层、翻译表、重构一律不做；重复是现状，不是待办。

## 三 反抽象与可验证

- 解释实验结果与新概念，不得用抽象总结、术语表格、方法论框架。改实况走查（一道真题：题目 → 各方法实际返回 → 白话总成绩）或一句话定义 + 两步流程 + 实际例子。
- 外部选型与 AI 对比表先核实真实数据（版本、发版时间、下载、反向依赖）再采信。
- 评审与结论必须对照代码现状再断言，不凭记忆或旧版本印象。

## 四 决策与请示

- 「不要让我判断，你自己判断并且做完」＝方案取舍全由 AI 决断，按最简方案一次执行到底，完成后只报告变更。呈现对齐方案不等于授权执行。
- 用户对设计级问题坦陈纠结时给本体级判断、不罗列选项。
- 用户问「你是否认可」时，先给认可与否的正面结论加理由，等 yes 再执行。
- 必须停下问的只有两类：不可逆的破坏性操作、未获明示的跨仓库推送；其余一律不问。

## 五 先报告留档再动手

- 「这个没用，反思设计偏差」＝先 grep 全部牵连点，写带日期的设计偏差反思归档后再动代码；不解释、不辩护、不只道歉。
- 发现名不副实只报告，不得自行改名或改术语；命名归用户。

## 六 工程纪律

- 「提交所有更新」＝逐层执行到底：子模块 → 父仓库指针 → 根仓库指针，不再逐次询问。分离头指针用 `git push origin HEAD:main`。
- 提交前核对全量暂存清单，只提交本次相关路径。
- 用户明示某规则长期生效时，落点是仓库 AGENTS.md，不进记忆库、不只留口头约定。
- workflow 不得手动触发；部署类限「主分支提交或 PR」。
- 入仓前脱敏：人员信息（人名、邮箱、部门名）与部署敏感（域名、桶名、CDN、账号、密钥）一律移除或改写。
- 不得运行关机、重启一类破坏性命令。
